# Supported games

Servyx is a library of games, not a single-game tool: every server it
adopts, monitors, or controls is driven by a `servyx.dev/v1` `GameDefinition`
YAML file under `definitions/`, loaded generically by
`FileSystemGameDefinitionProvider`. This page is a per-game reference for
what ships today. See [the schema reference](schema.md) for the full field
definitions, and the `/games` page in a running Servyx instance for the live
catalogue.

Some behaviour below is marked **UNVERIFIED**: it is what the definition
author believes the workload does, based on community documentation rather
than a captured, real reply. Every unverified reply-parsing shape is written
to degrade honestly (an unresolved or count-only result, never a thrown
exception or a mis-attributed player) rather than presented as confirmed —
see `docs/schema.md`'s "Player-list parsers" section for the isolation
guarantee this relies on. Treat an UNVERIFIED item as "tighten this once a
real server has been captured," not as a bug.

## Palworld

**Definition:** `definitions/palworld-docker.yaml` · **id:** `palworld`

| | |
|---|---|
| Docker image | `thijsvanloef/palworld-server-docker:latest` |
| Ports | `8211/udp` (game), `27015/udp` (A2S query), `25575/tcp` (RCON), `8212/tcp` (REST) |
| Control protocol | Source RCON (`source-rcon`), Palworld's own REST API (`palworld-rest`), A2S query |

**Deployment profiles:** two — `docker-thijsvanloef` (the Docker image;
`.env` is authoritative, `PalWorldSettings.ini` is regenerated by the
image's entrypoint on every restart) and `native-steamcmd` (bare metal via
SteamCMD; the INI is authoritative directly, with no regeneration step).

**Notable quirks:**

- The bundled image's own `HEALTHCHECK` calls `/v1/api/info` without admin
  credentials and gets `401 Unauthorized` on every probe, so Docker reports
  the container unhealthy while the game runs fine. The definition declares
  `lifecycle.healthSignal.trust: ignore` with an explanation shown to the
  operator — the only shipped definition that needs to override this signal.
- Three control channels: RCON for lifecycle/admin commands, REST for reads
  (preferred over RCON when both are reachable), and a bare A2S query
  channel with no authentication.
- Ships a foreign-backup adopter (`backup.adopt`) for the image's own daily
  cron rotation of `.tar.gz` archives — the only shipped definition that
  declares one.
- The player-list parser (`rcon.players`, `csv-with-header`) is **not**
  marked unverified — its three-column shape (`name,playerUid,steamId`) is
  confirmed.

## Minecraft (itzg)

**Definition:** `definitions/minecraft-itzg.yaml` · **id:** `minecraft-itzg`

| | |
|---|---|
| Docker image | `itzg/minecraft-server:latest` |
| Ports | `25565/tcp` (game), `25575/tcp` (RCON) |
| Control protocol | Source RCON |

**Notable quirks:**

- The mirror-image case relative to Palworld: `env` is authoritative **and**
  `server.properties` is a `derived` surface the image's entrypoint rewrites
  from `env` on every start — proving the role-based surface model handles
  either truth direction without a code change.
- The only shipped definition with a `backup.resume` block: the canonical
  Minecraft `save-off` → `save-all flush` → copy → `save-on` sequence, so a
  quiesced backup can never leave autosave disabled for the rest of the
  server's life. See `docs/schema.md`'s "Quiesce and resume".
- `stopGracePeriodSeconds: 200` against a `lifecycle.stop` ladder budgeting
  180s (`save-all` → `stop` → `SIGTERM` → `kill`).

**UNVERIFIED:** the `rcon.list` `summary-line` parser's exact reply text —
community tooling reports "There are N of a max[ of] M players online[:][ names]",
but the optional " of" and trailing colon are known to vary by server
version. The pattern is written permissively and a mismatch degrades to an
unresolved result; it cannot affect readiness (the `control-probe` fallback
only substring-matches `players online`, stable across the variants) or the
stop ladder.

## ARK: Survival Ascended (acekorneya)

**Definition:** `definitions/ark-asa-pok.yaml` · **id:** `ark-asa-pok`

| | |
|---|---|
| Docker image | `acekorneya/asa_server:2_1_latest` |
| Ports | `7777/udp` (game), `27020/tcp` (RCON) |
| Control protocol | Source RCON |

**Notable quirks:**

- Runs the Windows-only ASA dedicated server binary under Proton on Linux,
  which boots markedly slower than a native Linux binary — the readiness
  timeout is sized generously (20 minutes) for that alone, not because the
  log line itself is uncertain (it's confirmed verbatim).
- `GameUserSettings.ini` is modeled `authoritative`, not `derived` — unlike
  Palworld's/Minecraft's regenerated-on-boot config files, this one persists
  across restarts and is hand-editable, so nothing regenerates a Servyx
  write out from under it.
- No `control-probe` readiness fallback, unlike every other shipped
  definition. This is deliberate: a control-probe's `expect` string is
  matched verbatim, and — per the unverified note below — the exact RCON
  reply text this definition could probe with was never confirmed. Gating
  readiness on an unverified string risked a false negative blocking startup
  forever, judged worse than the log-regex-only fallback's own worst case.
- Four-stage stop ladder (`SaveWorld` → `DoExit` → `SIGTERM` → `kill`),
  longer than Palworld's or Minecraft's, because a bare SIGTERM alone loses
  world state for this game.
- No `deployments[].detect.requiredMounts` beyond the one save-data mount,
  and no separate query/A2S channel — ASA exposes player/status queries only
  through RCON.

**UNVERIFIED:** the `rcon.players` `lines` parser's exact `ListPlayers`
reply text — believed to be one numbered line per player
(`N. PlayerName, SteamID`) with a "No Players Connected"-style empty-server
line, but not checked against a captured fixture.

## Factorio (factoriotools)

**Definition:** `definitions/factorio-factoriotools.yaml` · **id:** `factorio-factoriotools`

| | |
|---|---|
| Docker image | `factoriotools/factorio:stable` |
| Ports | `34197/udp` (game), `27015/tcp` (RCON) |
| Control protocol | Source RCON |

**Notable quirks:**

- The motivating case for `deployments[].files[]`: the image generates a
  *random* RCON password into `/factorio/config/rconpw` unless that file
  already exists on first boot. The definition seeds it with a known secret
  before the entrypoint ever runs, so Servyx can authenticate RCON with a
  value it actually knows, rather than one the container invented:
  ```yaml
  files:
    - path: "${DATA_DIR}/config/rconpw"
      mode: "0600"
      createOnly: true
      contentFrom: "secret:rcon-password"
  ```
- The only shipped definition using a `format: json` config surface
  (`server-settings`, addressed via RFC 6901 JSON-pointer bindings like
  `/visibility/public` rather than a flat key or ini member).
- Factorio's Source RCON dialect exposes **no** quit/stop/exit command at
  all — verified, not a gap in the definition — so the stop ladder is only
  three stages (`save` → `SIGTERM` → `kill`), with `SIGTERM` budgeted 240s
  since it now carries the full weight of both the save and the process
  teardown.
- The primary readiness detector is a `control-probe` with `expect: ".*"` —
  deliberately reply-text-agnostic: what actually gates readiness is "RCON
  accepted a connection, authenticated with the seeded password, and
  returned *something*," not a guess at an unconfirmed reply.
- `ignored` (declared-only; see `docs/schema.md`) lists
  `map-gen-settings.json`/`map-settings.json`, which apply only at
  map-generation time and have no effect once a save exists.

**UNVERIFIED:** the secondary `log-regex` readiness fallback
(`'Hosting game at IP ADDR:\(0\.0\.0\.0:\d+\)'`), the `rcon.players` `lines`
parser's exact `/players online` reply text, and the `crashDetection`
pattern (generic native-crash signatures, not checked against a real
Factorio crash trace) — none of these gate readiness alone (the
control-probe above is primary) or can affect anything outside their own
narrow purpose.

## Not yet supported

**Satisfactory** is not a supported game today and is not planned as a
near-term addition. Satisfactory's dedicated server exposes no RCON-style
control protocol — only an HTTPS API — and Servyx has no HTTPS-API control
adapter implemented. Adding Satisfactory support would require building
that adapter first; until then, do not expect a `definitions/satisfactory*.yaml`
file to appear or work.
