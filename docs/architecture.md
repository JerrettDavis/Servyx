# Servyx Architecture

Servyx is a FOSS, self-hosted, pluggable, multi-game server control panel. It is
MIT-licensed, built on .NET 10 with a Blazor front end, and designed so that
adding support for a new game is a data-only exercise in the common case
rather than a code change.

This document describes the core domain model and the abstractions that
implement it. It reflects the following locked decisions:

- **Name:** Servyx.
- **License:** MIT.
- **Milestone 1 is strictly read-only** against live servers — no writes of
  any kind reach a managed workload until later milestones enable them
  explicitly.
- **Persistence:** SQLite with WAL mode by default; PostgreSQL is an opt-in
  alternative.
- **.NET Aspire is a dev-time tool only.** The shipped artifact is a Docker
  Compose file or a single binary — Aspire never appears in production
  topology.

## The Central Idea: Configuration Surfaces Carry a Role

The idea that shapes the rest of the domain is that every configuration
surface a game server exposes — an `.env` file, a `compose.yaml`, a rendered
INI, a live RCON/REST endpoint — carries a **role**, and that role is modeled
as a first-class domain concept rather than special-cased inside individual
adapters:

| Role | Meaning | Example |
|---|---|---|
| `Authoritative` | Servyx may write to this surface. It is a genuine source of intent. | `.env`, `compose.yaml` |
| `Derived` | Generated by the workload itself at boot. Servyx reads it for drift detection but **must never write to it** — writes would be silently discarded or would fight the workload's own generator. | Palworld's `PalWorldSettings.ini` |
| `Runtime` | Live state observed over RCON/REST. Read-only by nature. | RCON `ShowPlayers`, REST `/v1/api/settings` |

### Motivating case

The `thijsvanloef/palworld-server-docker` image renders roughly 150 `.env`
variables into a single-line `OptionSettings=(...)` blob inside
`PalWorldSettings.ini` on every container boot. Any write Servyx made
directly to that INI file would be silently overwritten the next time the
container started — the INI is a *derived* artifact, not a place to express
intent.

Tools built around Pterodactyl/Pelican's egg format have no way to express
this distinction. This is precisely why the Pelican Palworld egg ships an
empty `config.files` block and instead bundles a separate, compiled
`PalworldServerConfigParser` binary to work around the gap. Servyx models the
distinction in the domain itself so no adapter has to work around it.

## Core Abstractions

### `IExecutionTransport`

Represents a way to reach and act on a target host or workload. Declares its
capabilities via a `TransportCapabilities` flags enum:

- `ProcessLifecycle`
- `ContainerLifecycle`
- `InteractiveStdin`
- `FileTransfer`
- `ResourceMetrics`
- `ExecInWorkload`
- `PortForwarding`

Implementations include local Docker (over the `npipe` transport, using the
`desktop-linux` context), local process execution, SSH, and Docker-CLI-over-SSH.

`ProbeAsync` is required to be **side-effect free** — probing reachability or
capability must never itself mutate anything.

### `ITargetSession`

A session against a specific target, exposing:

- `ICommandRunner`
- `IFileGateway`
- `IWorkloadController`

Sessions are pooled and reference-counted rather than created per call.

### `CommandSpec`

Commands are expressed as an **argv array, never a shell string**. This is
the primary defence against command injection driven by game/definition
authors — remote implementations (e.g. over SSH) quote each argument
individually rather than interpolating into a shell line.

### `IFileGateway`

`ReplaceAsync` is atomic: it writes to a temporary sibling file and renames it
into place. It returns the pre-image SHA-256 hash so callers can build
revertible snapshots, and it accepts an `ExpectedPreImageHash` parameter for
optimistic concurrency — if the on-disk hash no longer matches what was
previewed, the file has drifted since preview and the write is **refused**.

### `IWorkloadController`

Encodes a `StopPlan` escalation ladder: **rcon → console → signal → kill**.
Each stage is given its own timeout, and the controller escalates to the next
stage only after the current stage's timeout elapses. It returns which stage
actually stopped the workload.

### Readiness vs. Container Health

**Container health must not be conflated with game readiness.** The
motivating evidence: the `thijsvanloef/palworld-server-docker` container's
own `HEALTHCHECK` curls `http://localhost:8212/v1/api/info` without admin
credentials, so it receives `401 Unauthorized` on every single probe
(observed `FailingStreak: 293`) — marking the container `unhealthy` while the
game server is running perfectly normally. `/v1/api/players` returns `OK` on
the very same polling cycle.

Two consequences follow:

1. Servyx derives readiness from its own declared detectors
   (`lifecycle.ready`: log-regex plus an authenticated control-probe
   fallback), **never** from Docker's health status. Docker health is still
   displayed in the UI, but as a separate, clearly labelled signal.
2. Any control-probe used for readiness **must carry authentication** — the
   `rest` channel's basic auth, or the `rcon` channel's `passwordRef`. A
   fallback probe that authenticates no better than the failing healthcheck
   above is worthless.

### `WriteGuardedTargetSession`

A decorator over `ITargetSession`. Its mutating members throw
`WritesDisabledException` before any I/O occurs whenever the target server's
`WriteMode` is `ReadOnly`. Individual services are never trusted to check the
write-mode flag themselves — the guard is structural, not a convention. An
architecture test asserts that no transport can be registered in DI without
this decorator wrapping it.

The `WriteMode` enum carries three values with distinct semantics:

- **`ReadOnly`** — Mutating transport calls (file writes, deletes, process starts, lifecycle operations) throw `WritesDisabledException` before any I/O occurs. Only reads and read-only control commands pass.
- **`PreviewOnly`** — Plans may be computed and diffs rendered via `PreviewAsync`, but `ApplyAsync` refuses to run.
- **`Enabled`** — Writes are permitted, subject to per-plan approval and audit logging.

### `IConfigFormatAdapter`

Round-trip fidelity is a hard requirement: `Render(Parse(x)) == x`
byte-for-byte, including comments, blank lines, key order, and quoting style.

### `IConfigValueCodec`

Decodes a structured payload that lives inside a single scalar value. The
motivating example is `unreal-option-settings`, which decodes Unreal Engine's
`OptionSettings=(...)` blob into named members.

### `SettingState`

A record with four columns, mirroring the surface roles above:

- `Desired` — Servyx's intent, as stored in the database.
- `Authoritative` — the current value of `.env` (or equivalent).
- `Rendered` — the current value of the generated INI.
- `Runtime` — the live value on the running server.

Alongside these, a `DriftKind` flags enum captures which columns disagree:
`DesiredVsAuthoritative`, `AuthoritativeVsRendered`, `RenderedVsRuntime`,
`Unreadable` — plus a `PendingRegeneration` flag for when a restart is needed
before drift can resolve.

### `IConfigMerger`

`MergePolicy.PreserveUnknown` is the non-negotiable default: keys Servyx does
not manage are never touched, reordered, or reformatted. For unstructured
files, managed regions are delimited with marker blocks:

```
# >>> servyx:managed >>>
...
# <<< servyx:managed <<<
```

### `IPlanExecutor`

The single funnel through which **every mutation in the product** passes:

- `PreviewAsync` — read-only; produces a unified diff with secrets masked, a
  reversibility flag per action, the capabilities the plan requires, and any
  restart consequences.
- `ApplyAsync` — bound to a specific, already-approved plan id; throws
  `PlanStaleException` if any surface has drifted since the plan was
  previewed.
- `RevertAsync` — reverses a previously applied plan.

### `IGameControlChannel` / `IControlChannelReachability` / `IGameControlSession`

Protocol is deliberately separated from reachability, because on the
motivating target neither RCON (25575) nor REST (8212) is published to the
host network on the target container. Reachability is tried via an ordered
list of strategies:

1. `direct-tcp`
2. `docker-exec-tool`
3. `docker-exec-network`
4. `ssh-tunnel`
5. `container-network`

Every control command carries a `readOnly: true|false` flag. When a server's
write mode is `ReadOnly`, only `readOnly: true` commands are permitted —
`ShowPlayers`/`Info` pass, while `Save`/`Broadcast`/`Shutdown` do not.

### `IBackupProvider` / `IBackupAdopter`

`IBackupProvider` supports create, list, `PlanRestoreAsync`, restore, and
prune. `IBackupAdopter` handles backups Servyx did not create: adopted
foreign backups are listed, inspectable, and restorable, but are marked with
`BackupOwnership.Foreign` and are **never** pruned, moved, renamed, or counted
against Servyx's own retention policy.

### `IModSource`

`PlanInstallAsync` returns a set of hashed file operations before anything is
downloaded, so installs go through the same preview discipline as
configuration changes.

### `IGameDefinitionProvider` / `IDefinitionTrustEvaluator`

Definitions carry a trust tier: `Builtin`, `Verified`, or `Unverified`.
Servers pin a definition by **content hash**, never by a mutable version tag.

### Deliberately not in the relational store

- **Resource metrics** — kept in an in-memory ring buffer and exported via
  OpenTelemetry, not persisted to SQL.
- **Console output** — append-only, rotated files with an offset index.
- **Secret ciphertext** — lives in the secret store, not the relational
  database.

## Security Model

### Definition trust tiers

`Unverified` definitions are forbidden from declaring: shell steps, bind
mounts outside the data root, privileged mode, host networking, undeclared
egress, or any port publication without explicit per-port approval.

All definition-sourced strings are rendered to the UI as plain text and never
as `MarkupString` — this closes the XSS class described by CVE-2024-34067.

Install steps run inside a throwaway, non-root container with a read-only
root filesystem, all capabilities dropped, no access to the Docker socket,
and an egress allowlist.

Per-server uid/gid isolation is enforced, directly answering Crafty
Controller's shared-user failure mode.

### Secrets and audit

- `ISecretStore` addresses secrets by URN, e.g.
  `secret://server/{id}/admin-password`, and defaults to AES-GCM envelope
  encryption.
- A global redaction filter scrubs secrets from console output, logs, audit
  records, and diffs.
- Audit is a hash-chained, append-only log:
  `Hash = SHA256(PrevHash ‖ canonicalJson(payload))`.
- Authorization uses fine-grained scopes.
- Console and metrics sockets use short-lived, scoped HMAC tokens with a
  `jti` denylist.

### Refused by default

The following are refused unconditionally, regardless of trust tier or
configuration:

- Mounting the Docker socket into a game workload.
- `--privileged`.
- Host networking.
- Bind mounts outside the data root.
- Path traversal.
- Root workloads.
- Definition-declared shell execution on the panel host.
- Publishing RCON to the host network.
- Pruning foreign backups.
- Auto-updating definitions from a remote source.
- Deleting a backup without naming it explicitly.

## Plugin Model

Servyx supports three plugin tiers:

1. **Data-only YAML definitions.** The default path for roughly 95% of "add a
   game" work. If adding a game requires code, that is treated as a schema
   bug to be fixed, not a plugin to be written.
2. **In-process collectible `AssemblyLoadContext` plugins**, for transports,
   config format adapters, backup providers, mod sources, and Blazor UI
   pages. These run with full panel privilege, so they must be enabled
   individually by an administrator, with the assembly's SHA-256 shown and
   an explicit warning presented before enabling.
3. **Out-of-process gRPC plugins** (`servyx.plugin.v1`), for third-party or
   non-.NET authors. Servyx mediates all filesystem and secret access on
   their behalf. This is the recommended default for anything the operator
   did not write themselves.

`Servyx.Plugins.Abstractions` is versioned separately from the rest of the
solution under strict semver; a plugin whose major version does not match is
refused at load time.

## Project Layout

| Project | Responsibility |
|---|---|
| `Servyx.Domain` | Entities and all abstractions above. Zero I/O dependencies. |
| `Servyx.Application` | Use cases, the plan/preview engine, the write-mode guard. |
| `Servyx.Definitions` | Game definition schema, YamlDotNet binding, validation, signature/trust evaluation. |
| `Servyx.Config` | Format adapters, value codecs, merge logic, unified diff generation. |
| `Servyx.Protocols` | Source RCON, Palworld REST, A2S, the Minecraft RCON dialect, reachability strategies. |
| `Servyx.Infrastructure` | EF Core, secret store, audit sink, scheduler, snapshot store, backup providers. |
| `Servyx.Infrastructure.Docker` | Docker transport implementation. |
| `Servyx.Infrastructure.Ssh` | SSH transport implementation. |
| `Servyx.Infrastructure.Process` | Local process transport implementation. |
| `Servyx.Web` | Blazor UI. Sidebar: Games, Servers, Settings, Plugins, Mods, Backups, Users. |
| `Servyx.Plugins.Abstractions` | Separately-versioned plugin contract surface. |
| `Servyx.Plugins.Hosting` | Plugin loading and isolation (ALC and gRPC hosting). |
| `Servyx.Cli` | Command-line interface; destructive verbs default to `--dry-run`. |
| `Servyx.AppHost` | .NET Aspire orchestration — dev-time only. |
| `Servyx.ServiceDefaults` | Shared service defaults (telemetry, health checks, etc.). |

Tests mirror this layout 1:1, plus `Servyx.IntegrationTests`, which uses
Testcontainers — CI spins up its own Palworld container for these tests, it
never touches a user's own server.
